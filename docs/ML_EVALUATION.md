# SmartDesk AI — ML Evaluation Report

Generated by `ml/train.py` (also runnable as `manage.py train_models`, which records a
`ModelRun`). The machine-generated confusion matrices and per-class tables live in
[`ml/reports/evaluation.md`](../ml/reports/evaluation.md) and are regenerated on every training
run — read that file for the current numbers.

## Design

| Component | Choice | Rationale |
| --- | --- | --- |
| Text features | TF-IDF, 1–2 grams, 12k cap, `sublinear_tf` | Strong baseline on short support texts; fast enough for request-time inference |
| Classifiers | Logistic Regression, `class_weight=balanced` | Calibrated-ish probabilities, coefficients double as feature attributions |
| Priority extras | Customer tier token + urgent-lexicon hits | Lets the model learn tier-aware urgency without hand-tuned thresholds |
| Routing extras | Category token prepended | Routing is mostly category-driven; text breaks ties |
| Sentiment | VADER lexicon | No training data needed; transparent compound score |
| Reply drafting | TF-IDF cosine over resolved cases + tone-aware template | Conservative, auditable, no external API |
| Split | Stratified 80/20, `random_state=42` | Comparable metrics across tasks |

## Explainability

For LR tasks the serving layer returns `top_features`: for the predicted class,
`contribution_i = coef_i × tfidf_i(text)`, top-N positive contributions. The UI renders these as
chips on every prediction card ("why this category"), alongside the full probability vector.

## Human feedback loop

1. Agent opens a ticket → sees predictions with confidence + features.
2. Clicks **accept** (feedback row: `accepted=True`) or **correct** (requires corrected label).
3. `AgentFeedback` rows aggregate into `/api/ai/metrics/`: acceptance rate per task and most
   common corrections — a live proxy for precision that does not need labelled hold-out data.
4. Corrections also appear in the ticket audit trail (`FEEDBACK` action).

## Retraining workflow

```bash
python ml/generate_corpus.py        # optional: refresh/regenerate the corpus
python ml/train.py                  # train + evaluate + write report + joblib artifacts
# or, inside the backend env:
cd backend && uv run python manage.py train_models --notes "why retraining"
```

Then `POST /api/ai/reload/` (or restart the server) so the in-process cache picks up the new
version. `ModelRun` rows keep version, sizes and full metrics for the monitoring page.

**Intended production upgrade:** export `AgentFeedback` corrections (ticket text + corrected
label) into the training corpus. The schema already supports it — feedback stores the prediction
(task, model version) and the corrected label against a real ticket.

## Honest limitations

1. **Synthetic corpus.** 1,500 template-generated tickets. Perfect category/routing scores will
   not survive contact with real language; they demonstrate the pipeline, not production accuracy.
2. **Distilled priority labels.** The label function (keywords + tier + category) is what the
   model learns to approximate — improvements must start with the rule, not the model.
3. **VADER sentiment** misses sarcasm, understated frustration and non-English text.
4. **Retrieval drafts** can surface an only-loosely-similar case; similarity threshold (0.05)
   is deliberately permissive for demo recall. Agents must review.
5. **No drift detection yet.** The monitoring page shows static eval + live acceptance rate;
   population-based stability metrics (PSI) and scheduled eval-on-feedback are future work.
6. **Single-process artifact cache.** Multi-worker deployments need shared storage (S3/NFS) and
   a versioned load path.

## Future work

- Fine-tune a small transformer (DistilBERT) for category/priority once real labelled feedback
  exists; keep LR as the interpretable baseline for comparison.
- Embedding-based retrieval (sentence-transformers) for reply drafts + similar cases.
- Active learning: surface low-confidence predictions to agents first.
- Drift dashboard: rolling acceptance rate with control limits, feature-distribution shifts.
